THE STUDENT LIFECYCLE

From application to diploma, on one thread.

Every stage writes to the same student record, so the next office never has to ask what the last one decided.

▶ Watch the lifecycle overview

  1. Apply

    An application is reviewed per programme and session. Acceptance creates the student record.

  2. Report

    Check in for the session, online or in person, inside the reporting window.

  3. Enrol

    Core and common units are enrolled automatically. Electives wait for HOD approval.

  4. Pay

    Fees bill by class and session. The balance is always derived, never typed in.

  5. Be graded

    Weighted components become a grade, frozen once finalised and released only when approved.

  6. Graduate

    Degree audit checks credits and GPA, then nomination, approval, diploma and convocation.

THE REGISTRY

Six core areas, built around how a university actually operates.

Not a generic project-management shell with education vocabulary bolted on. Each area below is a group of modules that share one data model.

REG
Admissions & curriculum

Programmes, syllabus approval, and course scheduling — with per-programme approval so a course can be core for one degree and elective for another, without duplicating the catalogue.

  • Applications per programme and session, with supporting documents and transfer-credit evaluation
  • Session rollover clones the curriculum in one atomic step
EXM
Grading & examinations

Configurable weighting per course — 30/70 CAT-to-exam as the default, overridable per class — with automated timetabling, clash detection, and QR-verified admit cards.

  • Grades freeze at publish time, immune to later policy changes
  • Exam results need HOD approval before students can see them
  • Invigilator assignment with workload limits enforced
FIN
Fees & finance

Fee structures by class and session, statements, part-payments, and the registration hold that only lifts once an account clears — no separate finance office spreadsheet to reconcile.

  • Payments, charges, scholarships and refunds post to journal entries
  • Exam cards gate on account status automatically
RES
Residence & welfare

Hostel allocation by room capacity and gender, plus a grievance system that routes complaints — academic, harassment, facilities — to the right office and escalates automatically if it stalls.

  • Harassment cases route straight to the Dean of Students, skipping department level
  • Anonymous complaints stay anonymous to faculty
SOC
Clubs, council & societies

Membership, leadership terms, budgets and patron oversight for every registered society, plus student council elections and proposals — events routed for Dean of Students sign-off.

LEC
Lecturer & staff console

Class lists, results entry, invigilation duty, a live timetable and a case inbox — built for the person standing in front of a class, not repurposed admin tooling.

ARCHITECTURE

Built to be extended, not replaced.

Naet is ready to run, and built to be extended. The integration layer is generic: every subsystem — payments, ERP sync, notifications, events, news, PDF rendering and results import — follows the same pattern. Core holds abstract contracts. Implementations live in contrib/. Register one class and it works.

▶ Watch why it's built this way

ERP

Event-driven ERP integration

When something happens anywhere in the system, a dispatch fires on transaction commit, so the ERP never hears about a change that was rolled back. A background worker looks up each registered handler and runs it independently, logging every attempt.

60s→120s→240s→480s→exhausted · admin notified
# Event naming — model.action
payment.confirmed · enrollment.approved
payment.failed · reporting.submitted
deferment.created · result.published
student.graduated · enrollment.rejected
Sync to SAP, Oracle, a homegrown PHP system, or a Google Sheet — the layer doesn't care. Write one class extending AbstractERPTask, register it, done.
PLUGGABLE

Consistent contract across subsystems

Adding a new payment provider, notification channel, PDF engine, results source, calendar source, or news feed follows the same pattern everywhere. Timetable and exam schedulers can be swapped the same way. No provider-specific code ever lives in core.

  • payments
  • erp
  • notifications
  • events
  • news
  • pdf engine
  • results import

Each subsystem exposes an abstract base class, a registry, and a reference implementation in contrib/. Integrators write their backend alongside the base or in their own Django app; dynamic registration in apps.py ready() keeps third-party packages isolated.

Events and news also fall back gracefully: synced when a connector and workers run, live when nothing is stored yet, manual when there is no connector at all. A failing source never breaks a page.

The rule that keeps it clean: core contains only abstract contracts and generic orchestration. Implementations go in contrib/ or the integrator's own app.

    Deploying in Kenya means meeting Kenyan obligations.

    Naet collects sensitive personal data — national IDs, financial records, family information, and special category data under the Kenya Data Protection Act, 2019. Compliance isn't a checkbox; it's documented and reflected in the schema. Every regulator a deploying institution answers to is listed below.

    ODPCData protection registrationEvery deploying institution is a data controller under the DPA 2019 and must register with the Office of the Data Protection Commissioner before going live.
    CUEAcademic records retentionUniversities Act, 2012 — admission and academic records retained permanently and exportable on audit request.
    KRA7-year financial retentionFee receipts, payment records, and ledgers retained per Kenya Revenue Authority requirements. Payment references preserved.
    HELBEnrollment verificationSemester reporting model supports HELB enrollment confirmation exports for loan beneficiaries.
    KE-CIRTCybercrime reportingComputer Misuse and Cybercrimes Act, 2018 — role-scoped admin, password hashing, and audit logging on the application side.
    NCPWDAccessibilityPersons with Disabilities Act — WCAG 2.1 AA as the target for the student-facing portal.
    Retention schedules, student rights, breach response and a pre-launch checklist are laid out on the compliance page.
    QUESTIONS

    What registrars and ICT directors ask first.

    Where does our data live?

    That is the institution's decision. Naet can be self-hosted: PostgreSQL on your own servers, with uploads and audit history alongside it. Or it can be hosted by a vendor, which suits institutions with budget or ICT-staffing constraints. In both cases it is your institution's own instance and database, not a shared multi-tenant system, and the compliance page covers what to settle in a hosting agreement.

    Is it finished, or a starting point?

    It is ready for use, and open to custom features. The student lifecycle, grading, fees, exams, complaints and clubs are built and working, so an institution can deploy it for its core operations now. Beyond that, each university can commission features that fit its own rules: its own grading policy, integrations, reports and workflows. Staff-side case handling is rolling out in stages: Head-of-Department level is available today, with Dean, student council, Dean of Students and Registrar levels planned. The modules page marks what is live and what is planned.

    Can we connect it to our existing ERP or payment provider?

    Yes. Payments, ERP sync, notifications, events, news, PDF rendering and results import all use the same pattern: an abstract contract in core, your implementation in contrib/ or your own app. ERP syncs run in the background with exponential-backoff retries, so a slow external system never blocks a student.

    How does it handle personal data and consent?

    Access is scoped by role, identifiers are UUIDs, and special-category fields such as religion and ethnicity are documented as consent-based, with a recommendation to remove them if unused. Students can export their own data. Details are on the compliance page.

    Will students be scored by an algorithm?

    Not in any way that acts on its own. The planned analytics are rule-based and explainable, shown only to authorised staff with the reasons attached, and always reviewable by a person. Machine learning is held back until there are several years of data. See the analytics page.

    Grades themselves are not an algorithm either. A final grade is a transparent formula the institution configures: weighted components (for example CAT 30%, Exam 70%), each combined by a stated rule such as average of all, best N, or latest N. The score is then matched to a grading scale and a pass mark set per course. Incomplete results show as "in progress", never as a partial number.

    How are grades calculated, and can they be changed afterwards?

    One grading service produces every grade shown anywhere: the lecturer's results page, the student portal, the transcript, GPA and classification. They cannot disagree.

    Weighting schemes and grading scales are versioned. A published scheme can't be edited, only revised into a new version. The primary lecturer sets the assessment plan for a unit (how many CATs, marked out of what, how they combine) until results exist, and it locks once they do.

    Results move through a controlled path. CATs and similar assessments publish immediately. Exam and project results are submitted, approved by the Head of Department, then published. When a grade is finalised it is frozen together with the scheme, scale and pass mark that produced it, so later policy changes never rewrite past transcripts. A correction needs an explicit regrade with a recorded reason, and every change is kept in the audit history. An institution can also cap resit and supplementary scores at the pass mark.

    Can we use our own grading scale, weights and rules?

    Yes. Grading scales (score bands, grade points and letters), weighting schemes, pass marks and aggregation rules are configuration, not fixed code. Rules such as the progression GPA threshold and honours classification bands are held in one place so they can be adapted to your regulations. Anything beyond configuration can be built as a custom feature.

    Do we have to adopt every module?

    No. Fees, hostels, clubs and council are separate areas around the academic core. The fee module is also under consideration to move to a dedicated financial ERP, with the event layer keeping the two in sync.
